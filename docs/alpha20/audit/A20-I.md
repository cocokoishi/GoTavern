# A20-I — `/api/backups/chat/download` did not use the pinned `send()` contract

| Field | Value |
|---|---|
| **ID** | A20-I |
| **Severity** | Low (headers/Range/resume parity; the bytes are correct) |
| **Status** | FIXED on `a20/audit` (commit with this file) |
| **Source** | `internal/server/backups.go` `serveBackupsChatDownload` |
| **Lane** | A (production source audit) |

## Summary

Pinned's route is `res.download(filePath)` (`src/endpoints/backups.js:54`). Express's `res.download` →
`res.sendFile` → `send@0.19.0` with `acceptRanges:true`, `cacheControl:true`, `etag:true`,
`lastModified:true`, `maxAge:0`. That means the pinned download carries:

- `ETag: W/"<hex size>-<hex mtime in MILLISECONDS>"` (send's **stat** etag, not a content hash),
- `Last-Modified` from `stat.mtime`,
- `Accept-Ranges: bytes` and Range/206 support (a download manager can resume),
- `Cache-Control: public, max-age=0`,
- `Content-Type` from send's pinned mime lookup.

GoTavern hand-wrote the response: content-hash `ETag` (`httpx.WeakETag(body)`), no `Last-Modified`, no
`Accept-Ranges`, no `Cache-Control`, no Range support, and host-dependent `mime.TypeByExtension`
(Windows registry) for the type. Because the recorded ETag is a *different value*, any client or
extension that revalidates with pinned's ETag can never match.

## The fixture already recorded the oracle value — the comparator just did not compare it

`tests/oracle/sillytavern-1.19.0-backups.json`, step `backups.download.ok`, for a 42-byte
`chat_alpha.jsonl` with mtime 1700000000 (whole second):

```
status 200, contentType application/octet-stream, contentLength 42,
etag W/"2a-18bcfe56800"        (0x2a = 42, 0x18bcfe56800 = 1700000000000 ms)
contentDisposition attachment; filename="chat_alpha.jsonl"
```

The generic replay comparator (`compareUserDataResponse`) asserts only that an ETag is **present**:
`"the replay sent no ETag although pinned Node did"`. So the recorded value was never compared. This is
the "a gate that compares presence instead of identity" failure mode, and the fix closes it for this route
with an exact-value assertion.

## Reproducer

`internal/server/a20_backup_download_test.go::TestA20BackupDownloadMatchesTheRecordedPinnedSendContract`:
seeds the fixture's exact file (42 bytes, mtime 1700000000) and asserts the recorded pinned values —

`Cache-Control: public, max-age=0`, `Content-Disposition` filename, body bytes.

## Why POST is not given a 304 face

Express's `req.fresh` getter returns false for any method other than GET/HEAD, and this route is POST
only, so pinned never answers 304 here. The shared helper's `httpx.IsFresh` has the same method gate, so
routing through it preserves that (`TestA20VersionAnswersPinnedExpressFreshness` pins the GET/HEAD-only
rule elsewhere).

## User impact

- The download's `ETag` never equals pinned's, so conditional revalidation (an extension or a script
  keeping the pinned ETag) can never produce the pinned 304/no-body answer.
- No `Range` support: a browser download manager cannot resume a large chat backup download
  (pinned answers 206 to a Range request); the transfer restarts.
- No `Last-Modified`/`Cache-Control`; content type came from the host OS mime database rather than the
  pinned table (host-dependent behaviour where pinning exists).
The file bytes themselves were always correct, which is why no fixture failed.

## Fix

`serveBackupsChatDownload` now sets `Content-Disposition` and serves the file through
`sendPinnedFrontendStaticBytes` — the shared implementation of pinned `send()` that the extension/static
routes already use — with a `frontendStaticFile` carrying `size`, `open`, `read`, `modTime` and
`hasModTime`. That reproduces send's stat ETag, Last-Modified, Accept-Ranges, Cache-Control, the pinned
mime lookup and Range/206 in one place, so this route cannot drift from the static routes.

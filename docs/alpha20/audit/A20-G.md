# A20-G — character avatar mutations never invalidated the cached thumbnail

| Field | Value |
|---|---|
| **ID** | A20-G |
| **Severity** | High (user-visible stale core asset) |
| **Status** | FIXED on `a20/audit` (commit with this file) |
| **Source** | `internal/server/characters_write.go` — `serveCharactersEdit` (no thumbnail invalidation in the file-upload branch), `serveCharactersEditAvatar` (none at all), `serveCharactersDelete` (none) |
| **Lane** | A (production source audit) |

## Summary

Pinned SillyTavern caches generated thumbnails on disk and serves the cached file whenever it exists
(`src/endpoints/thumbnails.js`). Every route that replaces or removes the source image must therefore
unlink the cache entry; the pinned helper is

```js
// src/endpoints/thumbnails.js:83-92
export function invalidateThumbnail(directories, type, file) {
    const folder = getThumbnailFolder(directories, type);
    if (folder === undefined) throw new Error('Invalid thumbnail type');
    const pathToThumbnail = path.join(folder, sanitize(file));
    if (fs.existsSync(pathToThumbnail)) { fs.unlinkSync(pathToThumbnail); }
}
```

and the character routes call it as:

| pinned route | line | condition |
|---|---|---|
| `POST /api/characters/edit` | characters.js:1127 | only inside the `request.file` branch (a new picture was uploaded) |
| `POST /api/characters/edit-avatar` | characters.js:1174 | always (the route requires an upload) |
| `POST /api/characters/delete` | characters.js:1432 | after unlinking the card |
| `POST /api/characters/import` | characters.js:1591 | covered here already (`invalidateCharacterThumbnail`, characters_import.go:76-91) |

GoTavern had **no** `thumbnailsAvatar` removal in the first three: `grep thumbnailsAvatar internal/server`
finds only the import site and the thumbnail route/cleanup. `/thumbnail` serves the cached file whenever
one exists (thumbnails.go branch 8), so after replacing a character's image — or after deleting a
character and creating a new one under the same filename — the character list, every chat-message avatar,
the group-chat collages and the persona/character pickers keep rendering the OLD picture indefinitely. The
route's existing `cacheBuster.bust` does not help: `Clear-Site-Data` clears the BROWSER cache while the
stale bytes are on the SERVER (pinned does both for exactly that reason).

## Node oracle

The oracle is the pinned source itself, which is unambiguous here (thumbnails.js:83-92 plus the three
cited call sites). The effect is pure server-side cache state: pinned's observable is "after the route,
`fs.existsSync(<user>/thumbnails/avatar/<file>)` is false and the next `/thumbnail` regenerates". The
reproducer measures the user-visible consequence (the rendered colour) rather than the helper call, so it
cannot pass by calling the helper in the wrong place.

## User impact

- Replace a character's picture (edit with a new avatar, or crop a new avatar) → the character list, chat
  avatars, group collages and pickers keep showing the previous picture until the process is restarted
  with a fresh cache or the file is manually deleted. There is no browser workaround: the stale image is
  the server's cached file, and its URL/ETag may even be unchanged.
- Delete a character and create a new one under the same filename → the new character inherits the deleted
  character's thumbnail (wrong picture, potentially a different character's face).
- Disk litter: the stale thumbnail survives the card.

This is the P0-E class ("core visual assets must display correctly") in its stale form: the image displays,
but it is the OLD image after an explicit user edit.

## Fix

Three call sites, exactly the pinned conditions:

- `serveCharactersEdit` — inside the existing `parsed.stagedPath != ""` branch (file uploaded), next to
  `cacheBuster.bust`; an ordinary text-only edit does not touch the thumbnail.
- `serveCharactersEditAvatar` — after the card write succeeds, before the response (pinned order).
- `serveCharactersDelete` — after `DeleteUserFile` succeeds, before the chat-directory handling.

Each reuses the existing pinned helper `invalidateCharacterThumbnail(directories, avatarURL)`
(characters_import.go:85-91), which is `invalidateThumbnail(directories,'avatar',sanitize(file))`.

## Regression guard

`internal/server/a20_thumbnail_invalidation_test.go`: the positive control (backgrounds) plus the two
character legs, each asserting the RENDERED COLOUR of `/thumbnail` rather than the presence/absence of a
file, so a call placed before a failed write or on the wrong route cannot pass.

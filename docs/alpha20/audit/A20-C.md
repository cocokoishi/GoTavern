# A20-C — the provider transport follows 19 redirects, pinned follows 20

| Field | Value |
|---|---|
| **ID** | A20-C |
| **Severity** | Low |
| **Status** | FIXED on `a20/audit` (commit with this file) |
| **Source** | `internal/outbound/transport.go:232-246` (`buildProductionClient`'s `CheckRedirect`) |
| **Lane** | A (production source audit) |

## Summary

Pinned provider traffic runs on node-fetch 3.3.2. Its redirect contract, read from the pinned package:

```
node_modules/node-fetch/src/request.js:134   follow default 20
node_modules/node-fetch/src/index.js:178     if (request.counter >= request.follow) { reject('max-redirect') }
node_modules/node-fetch/src/index.js:189     counter: request.counter + 1   // on the followed redirect request
```

`counter` starts at 0 and is incremented when a redirect is FOLLOWED, so `counter >= follow` first holds
on the response to the 21st request: node-fetch follows exactly **20** redirects and refuses the 21st.

Go calls `CheckRedirect(next, via)` before following each redirect, with `via` = every request issued so
far (length N before redirect N). The code used `if len(via) >= productionRedirectLimit` (20), which is
true at redirect 20 — so it followed only **19** and a chain of exactly 20 failed where pinned succeeds.
The correct bound is `len(via) > 20`.

The alpha.15 test that introduced the limit could not see this: it pins a 12-redirect chain (allowed under
both bounds) and an endless loop (refused under both). The boundary between 19 and 20 was never measured.

## Reproducer

`internal/outbound/a20_redirect_limit_test.go`:

- `TestA20ProductionTransportFollowsPinnedTwentyRedirects` — a server that redirects 20 times then
  answers JSON; asserts success, the body, and that the peer received exactly 21 requests.
- `TestA20ProductionTransportRejectsTheTwentyFirstRedirect` — an endless chain; asserts an error naming
  the redirect failure and that the peer received exactly 21 requests before the client gave up.


## Node oracle

The pinned package itself is the oracle: `node-fetch@3.3.2` in `SillyTavern/node_modules/node-fetch/src/`
(`request.js:134`, `index.js:178`, `index.js:189` quoted above). The Go test's request count (21) is the
same number node-fetch issues (initial request + 20 followed redirects, then a 21st response refused).

## User impact

A provider or CDN that answers a chain of exactly 20 redirects (the boundary case) fails with
"provider redirected 20 times; giving up" in GoTavern where pinned node-fetch completes the call. The
difference is narrow — 19 hops work, 20 do not — but it is a provider-wire availability divergence, not a
cosmetic one, and it is the kind that only appears behind a real CDN chain.

## Fix

`internal/outbound/transport.go`: `len(via) > productionRedirectLimit`; the error message now reports the
number of redirects actually followed (`len(via)-1`) so it stays truthful at the new boundary. The
comment carries the `counter`/`follow` derivation and names the measured boundary.

The CORS proxy's own redirect bound (`internal/server/cors_proxy_transport.go`, `len(via) > 20`) was
checked against the same contract and is already correct; it was not touched.

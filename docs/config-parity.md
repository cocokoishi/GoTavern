Every effective leaf key in the pinned default configuration has exactly one row below. The
classification vocabulary is the mission vocabulary: `implemented` means a named Go test fails if
the behaviour is removed; `explicit-no-op-with-startup-warning` means the key is carried and a
non-default value prints a named warning; `explicit-unsupported` means a documented decision not to
port the behaviour; `inherited` means this lane has no key-level behaviour evidence and the row is
the explicit work list rather than a parity claim; `not-applicable` means the pinned subsystem is a
documented architecture exclusion.

## Category definitions

- **implemented** — GoTavern reads the key on the same code path as the pinned server AND a named Go test fails if the behaviour is removed.
- **explicit-no-op-with-startup-warning** — GoTavern parses and preserves the key but does not implement its behaviour; an operator who sets a NON-DEFAULT value gets a named startup warning from internal/commandline/unimplemented_config.go (bounded, deterministic order).
- **explicit-unsupported** — GoTavern parses and preserves the key, the pinned behaviour is deliberately NOT ported, and the reason is recorded in docs/config-boundaries.md / the architecture boundary list. No warning is emitted because the shipped default is inert in pinned too or the warning would fire on every stock boot.
- **inherited** — The key is carried by the config pipeline (read, inserted, migrated or preserved) but this lane has NO dedicated key-level behaviour evidence for it. This row claims value/wiring parity only, never behaviour; it is the explicit work list, and the default for an unclassified key rather than a silent pass.
- **not-applicable** — The key configures a pinned subsystem that GoTavern deliberately does not implement (documented architecture boundary), so there is no behaviour to reproduce.

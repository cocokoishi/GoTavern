## 5. Measurement protocol (PROPOSED, ABBA)

The before/after protocol for any optimization accepted in alpha.17+:

1. **Same subject identity.** Both arms must share OS/CPU/RAM/GOMAXPROCS/Go version, build flags, data
   generation commands and route parameters; each arm records its binary sha256. A different sha256 is the
   point of the pair; a different host/build flag invalidates it (`GOAL.md` §15.2).
2. **ABBA alternation, >=3 rounds.** Round order A(arm=baseline), B(arm=candidate), B, A — then repeat.
   Every arm gets a fresh, byte-identical data root per round (the harness regenerates or copies it; a tree
   is never reused, `scripts/a15-bench-suite.mjs:641-661`). Alternation is what separates a host-load drift
   from a product effect on a shared host.
3. **Same-input selection.** The benchmark/harness input is fixed before the first arm and recorded: for
   in-process benches the benchmark name and scale, for process-level rows the scale, `--requests`,
   `--data-route` and `--rounds`.
4. **Statistics.** Publish per-arm medians and the full per-round series, plus p50/p95/p99 where the harness
   records them; report **both directions** (an improvement and a regression are both findings). No
   `benchstat` exists in this repository (`docs/alpha16/m5-evidence.md` §7.6); deltas below the host's
   measured spread are not claimed as wins.
5. **Artifact naming.** `docs/alpha17/perf/<kind>-<UTC stamp>.json` for single-arm baselines;
   `docs/alpha17/perf/abba-<metric>-<arm>-r<round>-<stamp>.json` for paired arms, so the arm and round are
   readable from the filename alone.
6. **Raw retention.** Every harness writes one self-describing JSON artifact containing environment,
   subjects, parameters, per-record samples and the artifact path; it is copied under `docs/alpha17/perf/`
   unmodified (no hand-edited numbers). Generated data trees are never committed.

For this round only the baseline arm was executed, so the pair is **one-sided**: no after arm exists
(§9), and no number here is presented as a before/after.

## 8. Thresholds derived from THIS baseline (PROPOSED, unratified)

### 8.1 Derivation arithmetic

No threshold below was chosen in advance. The rule, applied per metric over the six 100-card boots
(3 cold + 3 warm), is:

```
ceiling% = ceil( max(25, 200 × (max/min − 1)) )        # max/min over the measured records
```

`200 × (max/min − 1)` is twice the largest same-code spread this baseline observed: a two-sided pair on a
shared host must tolerate one observed spread on each side. The 25% floor exists because sub-percent
deltas are below this host's resolution and because alpha.16 derived the same 25% floor for latency
families (`docs/alpha16/m5-evidence.md` §6.2). A ceiling **wider than the observed spread is a detection
floor, not a budget**, and every row stays UNRATIFIED until a same-SHA repeated series exists (§8.3).

| metric | min | max | max/min − 1 | derived ceiling |
|---|---|---|---|---|
| cold boot (3) | 433.22 ms | 470.62 ms | 8.63% | **25%** (floor) |
| warm boot (3) | 117.65 ms | 152.85 ms | 29.92% | **60%** |
| RSS steady (6) | 29,601,792 B | 35,749,888 B | 20.77% | **42%** |
| peak RSS (6) | 36,167,680 B | 38,711,296 B | 7.03% | **25%** (floor) |
| `/version` p50 (6) | 6.45196 ms | 11.08752 ms | 71.85% | **144%** |
| `/version` p95 (6) | 17.21124 ms | 20.90788 ms | 21.48% | **43%** |
| `/version` p99 (6) | 18.94128 ms | 54.68012 ms | 188.68% | **377%** |
| `/` p50 (6) | 28.16636 ms | 32.99460 ms | 17.14% | **35%** |
| `/` p95 (6) | 38.55352 ms | 49.74448 ms | 29.03% | **59%** |
| `/api/characters/all` p50 (6) | 65.63 ms | 74.11732 ms | 12.93% | **26%** |
| `/api/characters/all` p95 (6) | 78.17588 ms | 112.18392 ms | 43.50% | **87%** |
| `/api/characters/all` p99 (6) | 88.76852 ms | 136.37404 ms | 53.63% | **108%** |

Note the p50/p99 ceilings are wide because a 50-sample p99 is effectively the maximum (`p99 == max` in
every record here, visible in the table) and the host was loaded: these are detection floors for gross
regressions, not a budget. A later quiet-window series should tighten them, never retro-fit a green.

### 8.2 Scale rows have NO derivable threshold

Each §7.2 row is n=1. A single observation cannot derive a spread, so no ceiling is proposed for any scale
row; they are **single observations, unratified**, and a same-scale repeat series is the named next step.

### 8.3 Ratification procedure (not executed)

Dispatch/run the same row twice at the same commit, same binary sha256, same parameters. If the pair's
deltas stay inside half the derived ceiling, the ceiling stands; otherwise widen it to 2× the observed
spread and record both run identities. A pair straddling a runner-image rotation is not comparable and is
re-taken. No alpha.17 row has been ratified.

## 10. Hotspot plan (PROPOSED; the change itself is UNEXECUTED — see `docs/alpha17/perf-hotspot.md`)

### 10.1 Candidate

The measured baseline makes `GET /api/characters/all` at 10,000 cards the highest-ROI candidate:
boot 27,099 ms, RSS 925 MB, peak 1,024 MB, route p50 5,481 ms on one observation. Candidate cost sites,
from the tree: `internal/server/characters_card.go:252` (`readCharacterData`), `:268`
(`readCharacterDataStrict`, the alpha.15 cached path), and the identity-keyed cache in
`internal/server/characters_card_cache.go:126` (`loadCharacterCardTextCache`) / `:149`
(`storeCharacterCardTextCache`) with `characterCardCacheMemoryCost` at `:209`. The existing in-process
scales that would pin the change are `BenchmarkCharactersAllScale` (`internal/server/bench_test.go:645`,
100/1,000/10,000 cards) and `BenchmarkCharactersAll` (`:330`).

**No product change was made in this round** (the lead's deadline instruction: no product code at the
freeze). The required RED evidence exists as measured cost; the missing half is the profile and the
same-input before/after pair, both named as the next step rather than fabricated.

### 10.2 Next step for the cold-cache guard (DELIVERABLE D, UNEXECUTED)

The alpha.16 record said the cold-guard row is absent (`docs/alpha16/baseline/README.md:66-69`, `:194-195`;
plan §8 R7). Proposed guard, which does **not** change any existing benchmark semantics:

1. Add one benchmark to `internal/server/bench_test.go` — `BenchmarkCharactersAllCold` — that resets the
   card cache (`resetCharacterCardCache`, `internal/server/characters_card_cache.go:218`) at the START of
   each `b.N` iteration and then issues one `/api/characters/all` request, so every iteration pays the cold
   path; `b.ReportAllocs()` as in the other benches. A fresh tree per iteration is not needed because the
   cache reset is the coldness being measured and the tree bytes are identical across iterations.
2. Record it into the committed gate input by regenerating deliberately:
   `node scripts/bench-profiles.mjs --update-baseline --out-dir tests/perf/out` on the same runner image
   (this is an explicit baseline regeneration, never an automatic update), and commit the new
   `tests/perf/bench-baseline.txt` + raw run in one commit.
3. `GoTavern bench profiles` consumes the row automatically: `scripts/bench-profiles.mjs` selects
   `-bench Benchmark`, takes the median of `--rounds`, compares with `tests/perf/bench-baseline.txt`
   two-sided (ns/op ±60%, B/op ±15%, allocs/op ±15%), and fails when a benchmark is missing or appears. No
   workflow edit is needed; the gate is `.github/workflows/bench-profiles.yml` (read-only here).
4. Risk to state in the row: the cold path's ns/op includes one-time OS page-cache effects, so the first
   round after a fresh checkout may be slower; the three-round median is what is compared.

### 10.3 Next step for process-level pprof (UNEXECUTED)

The release-style binary has no pprof server exposed and must not grow one for measurement. Proposed
method: `go test ./internal/server -run=NONE -bench='BenchmarkCharactersAllScale|BenchmarkChatSummary' -benchmem -count=3 -cpuprofile=<tmp>/cpu.out -memprofile=<tmp>/mem.out` (in-process, same shapes as the
trees), plus an execution trace if needed; then `go tool pprof -top`/`-alloc_space` and record the top
sites with file:line under `docs/alpha17/perf/profiles/`. The process-level boot cost must be attributed
with a temporary instrumentation build in the work tree (never committed) or an exact `-cpuprofile` of a
test that reproduces the boot scan.

## 11. Provenance, limits, and defects found

### 11.1 Artifact index

`docs/alpha17/perf/runner-fingerprint.json` (2,398 B) and `docs/alpha17/perf/a15/*.json` (9 files,
10,484–39,716 B) are the raw record; `docs/alpha17/perf/baseline-summary.json` (37,444 B) is a mechanical
extract of every record (it adds no numbers of its own); `docs/alpha17/perf/README.md` is the index.

### 11.2 Defects and caveats observed (recorded, not worked around silently)

1. **Harness defect: `scripts/a15-bench-suite.mjs` aborts on its own `complex-preset` scale entry.**
   `modeScale`'s default list has `{ scale: 'complex-preset' }` with no `scaleArgs`
   (`scripts/a15-bench-suite.mjs:815`), and `prepareTree` spreads it (`...scaleArgs`, `:647`), so the run
   dies with `TypeError: scaleArgs is not iterable` **after** seven scales were already measured and
   **before** `writeArtifact` — the whole artifact is lost. This is a real harness defect, not a host
   artefact; it is outside this lane's write scope (`scripts/**`), so it is reported, not patched. The
   baseline was re-taken per scale with explicit `--scale` after observing it.
2. **PowerShell pipeline exit code.** The first smoke invocation piped the harness's stderr
   (`2>&1 | Select-Object`) and PowerShell surfaced `NativeCommandError`/exit 1 although the harness wrote
   its artifact and printed its summary (AGENTS.md verification rule 8). The harness's own status was not
   re-derived from the pipeline; the artifact's assertion-bearing payload is the evidence.
3. **`build.command` quoting was collapsed by argument passing** when collected: the artifact records
   `go build -trimpath -ldflags=-s` because the shell's nested double quotes were consumed. The exact
   executed command and the real flags are §3 and `build.flags`
   (`-trimpath -ldflags="-s -w"`). The binary sha256 is unaffected and is the identity that matters.
4. **Not a quiet host.** The window overlapped other lanes on a 2-logical-core host; the load label says
   so in every artifact. The §8 ceilings are widened by that, deliberately.
5. **Not a clean tree.** `environment.git` records the commit and the dirty-file count; the dirty files are
   other lanes' modified `scripts/**` plus this lane's untracked `docs/alpha17/perf/` and `tools/perf/`.
   The subject binary was built from the tree at `fd40ef7…` and the artifacts record that.

### 11.3 Honest limits

Absolute milliseconds are host- and load-relative and are **not** a claim about user hardware or Linux CI.
The process-level layer cannot observe Go heap allocation totals, so B/op stays the in-process benchmark's
number. One boot per scale row, `--requests 3`, two logical cores: the scale rows are detections, not
budgets. Windows stops are abrupt (`abrupt-windows`), recorded per record. No browser, no provider, no
Docker, no live network in this window.
